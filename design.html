Processing Order

Sequential Product Queue

One Claude session at a time. Products rotate fairly using least-recently-run first so no product starves waiting behind a busy one.

Queue Algorithm

-- Who goes next? SELECT p.* FROM products p WHERE p.status = 'ready' AND EXISTS ( SELECT 1 FROM features f WHERE f.product_id = p.id AND f.status = 'approved' ) AND NOT EXISTS ( SELECT 1 FROM runs r WHERE r.product_id = p.id AND r.ended_at IS NULL -- no active session ) ORDER BY p.last_run_at ASC NULLS FIRST LIMIT 1;

NULLS FIRST — products never run yet go before products that ran recently. Fair round-robin across all products.

Example: 3 products in rotation

TimeProduct runningQueue
10:00MyApp (never run)AppB, AppC waiting
10:45AppB (never run)AppC, MyApp waiting
11:10AppC (never run)MyApp, AppB waiting
11:50MyApp (oldest run_at)AppB, AppC waiting
12:30AppB (next oldest)AppC, MyApp waiting

Products with no approved features are skipped

If a product has no approved features it is never selected, even if it has the oldest last_run_at. It rejoins the queue automatically as soon as the PM approves a feature.

Poller Main Loop (simplified)
loop forever: ① Check auth if not claude_auth_healthy(): alert_pm("Re-login needed"); sleep(60); continue ② Discover any new folders PM registered for product in db.get_undiscovered(): discover_and_populate(product) ← reads folder, updates DB ③ Reset stuck features db.reset_implementing_over_2h() ← Fix #7 ④ Pick next product (sequential, fair) product = db.get_next_product() ← ORDER BY last_run_at ASC if not product: sleep(60); continue ← nothing to do ⑤ PR count gate if github.count_open_prs(product) >= 3: log("≥3 open PRs — waiting for PM to merge"); sleep(300); continue ⑥ GitHub PR reconciliation (fix stale DB state) for pr in github.get_merged_prs(product, since_last_run): db.update_feature(pr.feature_id, status="Pushed") ← sync DB to GitHub truth ⑦ Run one Claude session exit_code = run_claude_in_docker(product) ← blocks until session ends if exit_code == 0: db.update(product, last_run_at=now()) ← only update on CLEAN exit (R-S2) ⑧ Back to top → pick next product sleep(5)

Agent Workflow — Per Session

Defined in AGENT_WORKFLOW.md in each product repo. Claude reads this on every startup. Edit this file to change Claude's behaviour without touching the poller.

📖
Read All Context Files First Startup Fixes #3 #4
Read these in order, every session — no exceptions:
  • README.md — vision, goals, competitors, out-of-scope
  • ARCHITECTURE.md — existing patterns to follow. Never introduce a new pattern without PM approval.
  • CLAUDE.md — platform details, test command, folder rules

Heartbeat Monitoring

Poller runs git log --since="45 minutes ago" -- progress.md every 5 minutes. Empty result = Claude is stuck (hung loop, frozen container). Action: kill container, relaunch. Claude reads progress.md and resumes from "Last file written." If stale exceeds 2 hours → alert PM via webhook.

Failure Modes Fixed

System Hardening — 8 Fixes Applied

These gaps were identified by comparing ProductFactory against production systems (Devin, OpenHands, Cursor, Copilot Workspace) and industry research. All 8 are incorporated into this design.

1
Docker Sandboxing
Critical
Before
Claude ran --dangerously-skip-permissions directly on Windows localhost with full filesystem access. One bad session = data loss.
After
Claude runs inside a Docker container. Only the product directory is volume-mounted. Host SSH keys mounted read-only. Container destroyed after session. Blast radius contained to /workspace.
2
Test Coverage Illusion
Critical
Before
Claude wrote and graded its own tests. Tests verified what Claude thought it built, not what the spec required. Features could ship wrong.
After
After tests pass, Claude writes a mandatory "Verification Note" in progress.md: re-reads the original feature description and explicitly confirms the implementation matches the spec in 2–3 sentences. PM can audit this on GitHub.
3
Architectural Drift
High
Before
Over weeks, Claude introduced multiple data access patterns, different error formats, inconsistent naming. Each PR looked fine; the codebase slowly became incoherent.
After
ARCHITECTURE.md is generated by Claude — after the first batch (greenfield) or during Analysis Run (brownfield). PM reviews and corrects. Claude reads it before writing any code every session. Claude updates it when new patterns are introduced. PM is never asked to write it.
4
Context Window Amnesia
High
Before
Decisions made at session start (while reading README) faded as the session grew. Feature 3 could contradict decisions made for Feature 1.
After
After each feature, Claude writes a "Session State Summary" to progress.md: key decisions made, patterns chosen, what next features must know. On resume, Claude re-reads this summary — explicit context replaces fading memory.
5
Dependency Hallucination
High
Before
Claude could install any package. Non-existent packages cause Blocked status (detectable). Existing-but-wrong packages silently corrupt the product.
After
After any package install, AGENT_WORKFLOW.md mandates running pip-audit (Python) or npm audit --audit-level=high (Node) before committing. Vulnerabilities must be resolved first. Results logged in features.md audit column.
6
Silent System Death
High
Before
If the Windows service crashed, the PM had no notification. Progress stopped silently. Last-known DB status looked fine.
After
Dead-man's switch: if progress.md last push >2 hours during business hours → poller sends webhook alert to PM (email / Slack). Poller itself registers heartbeat with VM every 5 minutes. VM alerts PM if poller goes offline.
7
Implementing Status Crash Trap
Medium
Before
If Claude crashed mid-feature, that feature stayed Implementing forever. Poller skipped it on every poll. PM saw no error.
After
On every poller startup: UPDATE features SET status='Approved' WHERE status='Implementing' AND updated_at < NOW() - INTERVAL '2 hours'. Two lines of SQL. Feature automatically re-queued for Claude on next poll.
8
CLAUDE.md Scope Creep
Low
Before
No token budget on CLAUDE.md. Industry research shows Claude silently ignores rules beyond ~2,000 tokens. File grows over time without warning.
After
CLAUDE.md hard cap: 1,500 tokens (platform facts only). Poller checks token count on scaffold and warns PM if exceeded. Detailed conventions belong in AGENT_WORKFLOW.md (explicitly read by Claude) not CLAUDE.md (auto-loaded, size-limited).

Five Additions for Brownfield

🔬

1 — Analysis Run (one-time)

Runs once before any feature work. Special Claude session that learns the codebase.

PM triggers from website
📂
Explore Codebase StructureOnce
  • Walk directory tree — identify source, test, config, build file locations
  • Read package.json / requirements.txt / pyproject.toml — record all existing deps
  • Read git log --oneline -20 — understand recent activity
  • Identify test runner, test naming convention, existing test count
🧪
Run Existing Test Suite — Record BaselineOnce
  • Run full test suite. Record: passed, failed, skipped counts
  • Write baseline to product_config.json → baseline_tests
  • If baseline has failures: flag them in ARCHITECTURE.md as "Pre-existing failures — do not fix unless asked"
This baseline becomes the pass bar for all future features. A new feature is only Committed if: new tests pass AND existing test count does not decrease.
🏛️
Generate ARCHITECTURE.md from CodeOnce
  • Read 10–15 representative source files across the codebase
  • Document: data access pattern, error handling format, naming conventions, module structure, auth approach, logging style
  • Cite concrete examples: "Auth uses JWT via middleware/auth.py:32"
  • Mark any inconsistencies: "Two error formats found — use {code, message} (majority pattern)"
⚙️
Write product_config.jsonOnce
  • Map source dirs, test dirs, new feature paths, test command, audit command
  • Record baseline test counts
  • Commit ARCHITECTURE.md + product_config.json + features.md (existing features catalogued as ✅ Pushed)
👤
PM Reviews ARCHITECTURE.mdPM Action
  • PM reads the generated ARCHITECTURE.md — correct any misunderstandings
  • PM marks Analysis as "Reviewed" on website → unlocks feature approval
  • No features can be approved until Analysis is reviewed
If PM skips this review, Claude may base all future work on misunderstood patterns. This gate is enforced by the PM website — Approve button is disabled until Analysis = Reviewed.
🗺️

2 — Path Mapping via product_config.json

Existing apps don't follow ProductFactory's SRC/TestCases/Results layout. product_config.json tells Claude where everything is.

// product_config.json — brownfield example { "type": "brownfield", // where existing source code lives "source_paths": ["app/", "lib/"], // where existing tests live "test_paths": ["tests/", "spec/"], // where Claude adds NEW feature source files "new_feature_source": "app/features/", // where Claude adds NEW feature test files "new_feature_tests": "tests/features/", // results always go here (can be anywhere) "results_path": "Results/", // commands to run "test_command": "pytest tests/ -v --json-report", "audit_command": "pip-audit", // baseline recorded during Analysis Run "baseline_tests": { "passed": 127, "failed": 0, "skipped": 3, "recorded": "2026-03-29" } }

Greenfield product_config.json

{ "type": "greenfield", "new_feature_source": "SRC/", "new_feature_tests": "TestCases/", "results_path": "Results/", "test_command": "pytest TestCases/ -v", "audit_command": "pip-audit" }

Greenfield uses ProductFactory defaults. Scaffolded automatically by poller on first run.

Rule: Claude reads product_config.json before writing any file

New source files go to new_feature_source. New test files go to new_feature_tests. Claude never writes to existing source_paths directly unless the feature explicitly requires modifying an existing file.

🛡️

3 — Baseline Test Gate

A feature is only Committed if it passes its own tests AND does not break any existing tests.

Claude runs the full test suite (not just new tests) after implementing each feature. The pass condition is:

# Pass condition for brownfield new_tests_passed == True AND current_passing >= baseline_tests.passed

If a new feature causes any existing test to fail:

  • Claude attempts to fix the regression (counts as one of the 3 fix attempts)
  • If unfixable → status → Blocked
  • Blocked reason in progress.md: "Caused regression in test_X — see Results/regression_report.json"

✅ Greenfield test rule

Run TestCases/test_{feature}_{sub}.py only. No existing tests to break.

🏗️ Brownfield test rule

Run full suite every time. New tests + all existing tests must pass. Baseline count must not decrease.

Pre-existing failures

If baseline has failures (recorded during Analysis), those are excluded from the gate. Claude must not make them worse but is not responsible for fixing them unless asked.

🔒

4 — Scope Boundary

Claude must not touch files outside the feature's scope — no unrequested refactoring, no "while I'm here" fixes.

Before committing, Claude checks its own diff:

# Allowed changes in brownfield app/features/{feature}_{sub}.py ← new file ✅ tests/features/test_{f}_{s}.py ← new file ✅ features.md ← always ✅ progress.md ← always ✅ Results/{f}_{s}_results.json ← always ✅ # Requires justification in progress.md app/existing_module.py ← modified ⚠️ requirements.txt ← modified ⚠️ # Never touch *.lock · migration files ← blocked 🚫

If modification of existing file is unavoidable

Claude writes to progress.md before touching the file:

⚠️ Must modify app/auth.py
Reason: feature requires new OAuth scope
Change: add scope param to validate_token()

New dependencies

Claude checks existing requirements.txt / package.json first. If the needed package is not already present, Claude notes it in progress.md and flags to PM before installing. New deps must not conflict with existing lock file versions.

🔄

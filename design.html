Orchestration

Poller Cycle

Every 60 seconds (5s between products), the poller executes a 13-step cycle — pre-fetching and claiming features before Docker launch so the agent is a pure executor.

①
Auth Health Check
Runs claude -p ping --max-budget-usd 0.001. A "budget exceeded" response confirms auth is valid. Skips cycle if truly unhealthy, sends critical alert.
HEALTH GATE
②
Scaffold Greenfield Products
Creates GitHub repo, adds deploy key, clones to working directory, applies stack templates. Runs for any product in greenfield_pending state.
INFRA
③
Discover Registered Products
Reads CLAUDE.md, detects stack (python/node/go), installs templates (AGENT_WORKFLOW.md, ARCHITECTURE.md). Brownfield: sets status to ready immediately. Greenfield: sets to discovered for PM scaffold review.
INFRA
④
Heartbeat — Kill Stale Containers
Checks if progress.md was pushed within the last 45 minutes. If not, kills the container and sends a warning alert.
HEALTH
⑤
Reset Stuck Features
Features stuck in Implementing/Designing/Reviewing for >2 hours are reset back to Approved, unblocking the pipeline.
HEALTH
⑥
Deliver PM Messages
Writes pending pm_messages from product config into pm_message.md in the workspace. Claude reads this on startup.
MESSAGING
⑦a
Reviewer-First Priority Check
Globally scans all ready products for features in Reviewing state with an open PR. If found, immediately schedules a reviewer session — bypassing normal round-robin.
PRIORITY OVERRIDE
⑦b
Round-Robin Product Selection
If no reviewer work: picks the product with oldest last_run_at (fair scheduling). Also includes products with empty backlogs (for Planner).
SCHEDULING
⑦c
Persona Determination + Feature Pre-fetch
Queries /api/features/next-for-persona to pick designer or coder. Then fetches assigned features from PM API and PATCHes them to Implementing/Designing (claim-before-launch) so no other poller instance can double-claim. Injects {assigned_features} and {prev_session_summary} into the agent prompt.
ROUTING + CLAIM
⑧
Quiet Hours Gate
Skips designer/coder/planner during configured UTC quiet hours (e.g. 22–6). Reviewer always runs — code reviews are time-sensitive.
GATE
⑨
Daily Session Cap Gate
Tracks sessions launched per product per day in memory. If cap is reached, skips until the next UTC day. Reviewers are exempt from the cap.
GATE
⑩
PR Count Gate (Coder only)
If ≥3 open PRs exist on GitHub for this product, pauses the coder for 5 minutes and sends a warning alert. Prevents PR pile-up.
GATE
⑪
GitHub PR Reconciliation
Syncs merged PRs from GitHub → sets matching features to Pushed in the DB. Ensures DB state never drifts from GitHub reality.
SYNC
⑫
Launch Docker Session + Live Poll
Runs docker run --rm productfactory-agent with isolated bridge network, read-only OAuth + deploy key mounts. Streams logs to PM API. A background thread polls session_result.json every 30 s and applies each NDJSON line to the DB in real-time as the agent completes phases.
RUN + LIVE POLL
⑬
Reconcile + Auto-merge + Update last_run_at
After Docker exits: final NDJSON reconcile for any lines the live-poll thread missed. Rolls back features with no entry and no open PR. Triggers auto-merge for high-confidence reviewer approvals. Only updates round-robin pointer on clean exit (code 0).

Detailed Internals

Poller Session Workflow

A deep dive into what happens during one product session — from feature selection through real-time DB updates to post-container cleanup.

🔄
Phase 1 — Pre-Docker (Poller, on host)
Everything the poller does before launching the container. The agent receives pre-claimed features; it never self-selects work.
STEP 1
Fetch sys_cfg
Reads auto_merge_enabled and global config from the PM API before building the prompt — fixes a previous bug where {auto_merge_enabled} always rendered as False.
GET /api/system/config
STEP 2
Fetch Assigned Features
Persona-specific API call. Coder: /api/features/approved. Designer/Reviewer: /api/products/{id}/features filtered client-side. Limits to max_features_per_run.
_fetch_assigned_features(product_id, persona)
STEP 3
Claim Features (PATCH)
PATCHes each feature to Implementing (coder) or Designing (designer) before Docker starts. Prevents double-claiming if the poller polls again mid-session.
_claim_features(features, persona)
STEP 4
Read Session Summary
Reads session_summary.md from the product workspace for session continuity. Falls back to last 50 lines of progress.md if summary doesn't exist. Truncated at 2000 chars.
_read_session_summary(working_dir)
STEP 5
Build Prompt
Renders the persona-specific Markdown prompt with all substitutions now ready: {assigned_features}, {prev_session_summary}, {auto_merge_enabled}, {tech_stack}, {session_uid}.
build_prompt(product, session_uid, persona)
STEP 6
Launch Container
Starts docker run --rm with the rendered prompt as -p arg. Simultaneously starts a live-poll background thread and a log-streaming thread. Blocks until container exits.
docker run … claude -p "{prompt}"
▼ Docker container running ▼
⚡
Phase 2 — During Docker (Agent + Poller, parallel)
The agent implements features while the poller's background thread applies DB updates in real-time — no waiting until container exit.
🤖 Agent (inside container)
  • Reads AGENT_WORKFLOW.md, ARCHITECTURE.md, CLAUDE.md
  • Receives pre-assigned features in prompt — no API self-discovery
  • Implements each feature in order
  • Appends one NDJSON line to session_result.json after each phase completes
  • Writes session_summary.md incrementally throughout (not just at end)
  • Opens PR → appends "status":"Reviewing" line
  • Never calls PATCH /api/features/{id} directly (Option B)
🔄 Live-Poll Thread (on host, every 30s)
  • Runs in background alongside log-stream thread
  • Tracks applied_up_to line index — never reprocesses a line
  • Reads session_result.json on each tick
  • Applies any new NDJSON lines to DB via PM API immediately
  • On status: Reviewing: stores PR number + URL in DB
  • On status: Reviewed + confidence: high: schedules auto-merge
  • Stopped via threading.Event after Docker exits
session_result.json — NDJSON format (one object per line, append-only)
{"id": 42, "status": "Implementing"}
{"id": 42, "status": "Reviewing", "pr_number": 17, "pr_url": "https://github.com/…"}
{"id": 43, "status": "Blocked", "blocked_reason": "baseline tests dropped from 47 to 39"}
{"id": 44, "status": "Reviewed", "review_outcome": "approved", "confidence": "high"}
{"id": 44, "status": "Designed", "design_doc_path": "docs/feature_044_design.md"}
▼ Container exits (code 0 or non-zero) ▼
✅
Phase 3 — Post-Docker (Poller, on host)
Cleanup, final reconcile, auto-merge, and optionally the post-coder chain.
STEP 7
Stop Live-Poll Thread
Sets the stop threading.Event. Waits up to 5 seconds for the thread to join cleanly before proceeding to final reconcile.
_poll_stop.set(); poll_thread.join(5)
STEP 8
Final NDJSON Reconcile
Reads all remaining lines in session_result.json not yet applied by the live-poll thread (using the same applied_up_to pointer). Applies them to the DB. Idempotent — safe to re-apply already-seen lines.
_reconcile_session_result(working_dir)
STEP 9
Rollback Stuck Features
Any claimed feature (Implementing/Designing) that has no entry in session_result.json and no open PR is reset to Approved. Prevents features stuck in limbo after a crashed session.
_rollback_uncompleted(claimed, results)
STEP 10
Auto-Merge
If auto_merge_enabled and any feature was reviewed with confidence: high, merges the PR via gh pr merge --squash and sets status to Pushed. Low-confidence approvals are left for human merge.
gh pr merge {pr_number} --squash
STEP 11
Post-Coder Chain
On coder clean exit: runs QA Tester → Security Auditor. Each is a separate docker run in sequence. Recommender runs post-sprint (not here). Failures don't block the chain.
_run_post_coder_chain(product, session_uid)
STEP 12
Update last_run_at
Only updates the round-robin pointer if Docker exited with code 0. Failed sessions don't advance the queue — the product is immediately eligible for re-selection in the next poll cycle.
PATCH /api/products/{id} last_run_at=now()
▼ Session complete — next poll cycle begins in 5s ▼
Session Continuity via session_summary.md
Agents write session_summary.md incrementally throughout their run — startup, key decisions, completions, blockers. The next session receives this as {prev_session_summary} in the prompt. Fallback: last 50 lines of progress.md.
Option B — Full Poller DB Ownership
Agents never call PATCH /api/features/{id} directly. All DB updates flow through session_result.json → poller _reconcile_session_result(). The poller is the single source of truth for feature state transitions.
Claim-Before-Launch
Features are PATCHed to Implementing / Designing by the poller before docker run. If the poller polls again while the container is still running, those features are already claimed and won't be double-assigned.
Strict Single-Sprint Scoping
When an active sprint exists, agents only see features in that sprint — never features from future sprints. Newly approved features are auto-assigned to the next planned sprint (not the active one) to avoid scope creep mid-sprint.
Live DB Updates Every 30s
A background thread on the host polls session_result.json every 30 seconds. The PM dashboard shows real-time feature state changes mid-session — not just a batch update when the container exits.
Multi-Agent System

11 AI Personas

Each persona is a separate Docker session with a specialized prompt. They run in priority order — delivery pipeline first, then maintenance, then planning. Two additional personas are on-demand only.

Feature Delivery Pipeline — triggered by backlog state
✏️
Designer
Trigger: Approved features with skip_design=false
Writes detailed implementation-ready design documents before any code is written. Ensures the coder has clear acceptance criteria, file-level plans, data models, and testing strategy.
INApproved feature (skip_design=false)
OUTdocs/feature_NNN_design.md → status: Designed
⚙️
Coder
Trigger: Designed features or skip_design Approved
The core implementer. Reads design docs, implements features, writes basic tests, opens a pull request, and sets status to Reviewing. Uses greenfield or brownfield prompt based on product type.
INDesigned feature (or skip_design=true Approved)
OUTPR opened → status: Reviewing → triggers post-coder chain
🔍
Reviewer
Trigger: Reviewing features with a PR number (GLOBAL priority)
Reviews PR diffs against design docs and acceptance criteria. Runs security checklist, verifies tests pass. Either approves the PR or requests changes (sets back to Implementing for rework).
INReviewing feature with PR number
OUTgh pr review → status: Reviewed or back to Implementing
Post-Coder Chain — auto-runs after every successful coder session (PR-level)
🧪
QA Tester
Auto-trigger: immediately after coder succeeds
Finds the latest open PR, checks out the branch, reads the diff, and writes automated tests. Commits tests directly to the PR branch so the Reviewer sees full test coverage in the review.
INLatest open PR (gh pr list)
OUTtests/ files committed to PR branch
🔒
Security Auditor
Auto-trigger: after QA Tester
Audits the PR diff against OWASP Top 10 checklist: SQL injection, XSS, hardcoded secrets, missing auth, path traversal, command injection. Files bug features for every issue found. Comments audit result on the PR.
INPR diff (gh pr diff)
OUTBug features filed + PR comment + last_security_auditor_at updated
Post-Sprint Automation — run once after each sprint completes (gated by last_{persona}_at vs sprint.completed_at)
📝
Documenter
After each sprint completion (last_documenter_at)
Keeps README, CHANGELOG, and ARCHITECTURE.md in sync with what's actually been built. Writes for a new developer. Adds changelog entries for recently Pushed features.
INSource files + Pushed features list
OUTREADME.md + CHANGELOG.md + ARCHITECTURE.md updated
📊
Analytics
After each sprint completion (last_analytics_at)
Analyses feature velocity, backlog health, codebase growth, and UX gaps. Generates a structured analytics report in docs/ and files high-value feature suggestions backed by data.
INAll features + sessions + git log + codebase
OUTdocs/analytics_*.md + new feature suggestions
🔧
Refactorer
After each sprint completion (last_refactorer_at)
Scans the codebase for tech debt: god classes, duplicated logic, N+1 queries, magic numbers, dead code, missing abstractions. Creates specific chore features — never modifies code directly.
INSource files + existing features list
OUTChore features (priority 40) for PM approval
🏗️
DevOps
After each sprint completion (last_devops_at)
Reviews Dockerfile, docker-compose, GitHub Actions, and dependency manifests. Checks for pinned base images, non-root users, secret handling, CI coverage, and outdated major versions.
INDockerfile + workflows + requirements + .env.example
OUTInfra chore features (priority 50)
💡
Recommender
After each sprint completion (last_recommender_at)
Searches competitors via web, analyses what was just built in the sprint, and suggests new feature ideas aligned with market direction. Posts them as Pending with source="ai" for PM approval.
INSprint release notes + product context + web search
OUTNew Pending features (source: ai) + last_recommender_at updated
Backlog Generation — last resort when nothing else to do
📋
Planner
Trigger: no Pending/Approved/Designed/Implementing/Reviewing features exist
Reads the entire product context (ARCHITECTURE.md, CLAUDE.md, README, source files, existing features) and generates thoughtful new feature ideas. Creates them as Pending — the PM must approve before implementation begins.
INFull product context + existing feature list (to avoid duplicates)
OUTN new Pending features (source: ai, PM approves before coder picks up)
On-Demand / Special Triggers — bypass round-robin, run immediately when flagged

Product Trainer

INShipped features list (status: Pushed/Reviewed/Reviewing)
OUToutput/product_video_<timestamp>.mp4 committed + pushed

Analysis Run
Trigger: POST /api/products/{id}/trigger_analysis from PM dashboard
Deep brownfield codebase analysis — maps architecture, identifies technical debt, catalogues existing APIs and data models. Produces a structured report in docs/ for the PM to review before feature planning begins.
INFull repository source tree
OUTdocs/analysis_*.md + analysis_status: completed

Automation Chain

Post-Coder Pipeline

After every successful coder session, two agents run automatically in sequence — QA Tester and Security Auditor operate at the PR level. Recommender runs post-sprint (not post-coder).

⚙️
Coder
Opens PR · Sets Reviewing
🧪
QA Tester
Adds tests to PR branch
🔒
Security
Audits diff · Files bugs
🔍
Reviewer
Next cycle · Reviews PR
Exit codes don't block the chain. QA Tester and Security Auditor are best-effort — their failure doesn't prevent the Reviewer from running next cycle.
Tests land before review. QA Tester pushes tests to the same PR branch, so the Reviewer sees the complete implementation + test suite.
Security → PM backlog. Issues found by Security Auditor become bug features in the backlog (priority 90), approved and fixed in the next coder cycle.
Reviewer runs next cycle. After the chain completes, the Reviewer has global priority in the next poller cycle — it sees the tests added by QA Tester.

Security Model

Container Isolation

Each agent session runs in a minimal-privilege container. OAuth tokens and deploy keys are read-only mounts — the agent can never write to them.

🔒
Container Isolation
  • Bridge network (not --network host)
  • No --privileged flag
  • 4GB RAM, 2 CPU hard limits
  • 90-minute session timeout
  • Session lock file prevents duplicate launches
  • Auto-killed if stale (>45m no progress)
🗝️
Credential Handling
  • ~/.claude mounted read-only (OAuth)
  • Only the specific deploy key mounted (not all of ~/.ssh)
  • Known_hosts baked into image
  • GH_TOKEN injected as env var, not file
  • No secrets in Docker image or source
  • Per-product deploy keys (id_ed25519_{name})
🌐
Network Segmentation
  • productfactory-net isolated bridge
  • pm-api reachable via host-gateway alias
  • Ollama reachable as host.docker.internal
  • No direct internet from container by default
  • REST API has no auth (internal only)
  • PM dashboard uses HTTP Basic Auth (timing-safe)
🛡️
Gate System
  • Auth check before every poll cycle
  • Quiet hours prevent off-hours runs
  • Daily session cap per product
  • PR count gate (max 3 open PRs)
  • Stuck feature reset after 2h
  • Session lock file (session.lock)
🔍
Continuous Security Scanning
  • Security Auditor runs after every coder session
  • OWASP Top 10 checklist applied to every PR
  • SQL injection, XSS, secrets, auth checks
  • Issues filed as priority-90 bug features
  • PR comment with audit result (audit trail)
  • Reviewer also performs security review
🔄
Resilience
  • last_run_at only updated on clean exit (code 0)
  • Failed sessions get re-queued immediately
  • Ollama 500 errors: 3-attempt retry (2s sleep)
  • Stale container heartbeat check every cycle
  • GitHub PR reconciliation on every coder cycle
  • Alerts for auth failure, stale sessions, PR pile-up

Development

Local Development

Run the full agent loop locally without Docker or the Claude API using Ollama. Useful for testing new prompts and personas.

Quick Start
# Install deps
pip install -r requirements.txt

# Start PostgreSQL + PM website
docker-compose up -d

# Run migrations
alembic upgrade head

# Start poller (Windows)
python orchestrator/poller.py
Local Ollama Test Run
# Run coder session (no Docker, no API key)
python scripts/test_run.py \
  --product-id 3 \
  --working-dir /path/to/product \
  --persona coder

# With ad-hoc feature
python scripts/test_run.py \
  --feature "Add login endpoint" \
  --desc "POST /login → JWT token"
Note: gemma3:27b does not support tool use — use qwen3-coder:30b for all personas when using Ollama. Set DESIGNER_MODEL=qwen3-coder:30b in .env. Git Bash on Windows mangles paths starting with /app/ — use //app/ to prevent it.
